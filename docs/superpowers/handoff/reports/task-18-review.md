## 二、立即修（1）

### 立即修 1：转化分布和堆叠图遇到"累计值下降"时输出负数

位置：`src/pages/stat/guest/conversion.ts:29-36`（`bucketOf` 直接 `last - first`）、`:46`（分布求和）、`:67-75`（堆叠，含"第 3 日及以后" = 最后到期列 − `d2`）。

我跑了一行：`d0=10, d1=20, d2=18, d3=25, d5=24, d7=30, d14=35, d30=40` 的单个 cohort，得到分布 `D2 = -2`、`D4-D5 = -1`，堆叠 `D2 = -2`。

决定：这是错误输出，要修。理由：这些数是"累计转化设备数"，按定义不会下降，所以出现下降只能是后端数据出了问题（例如某天的设备记录被清理后重算、补数在不同时间写格子）；但图表上的"设备数"是个数，环形图的扇区、堆叠柱的高度不能是负数——负的扇区没有意义，也让总数和图例对不上。让运营在图上看到"-2 台设备"比看到 0 更糟。当前开发用假后端就会触发（见记录 7），所以浏览器里已经能看到负柱。

怎么修（不是可选项，选一种并带测试）：`buildConversionDistribution` 和 `buildConversionStack` 对每个档/段取 `Math.max(0, 差值)`；矩阵里的带符号"新增"不动（那是如实显示原始数据，`guest.test.tsx:439` 守着）。代价是下降的那部分在图上被吞掉，各档之和会大于最后到期列；这比负数可取，且仅在数据有问题时出现。测试要补：`d2 < d1` 时 `D2 = 0` 而不是负数；最后到期列小于 `d2` 时"第 3 日及以后"是 0。

后果（带着它上线）：后端一旦发出下降的累计值，环形图和堆叠柱出现负数扇区/负柱，运营会读出错误的"转化耗时分布"。我没有在真实浏览器里确认 G2 对负值扇区的具体画法，函数输出为负是已经复现的。

## 四、不是缺陷（6）

1. 缺格子时分布与堆叠算法不同：`d3` 缺失而 `d5` 有值时，分布里 D3 和 D4–D5 两档都不计该 cohort（`conversion.ts:29-36`，测试 `conversion.test.ts:97` 守着），堆叠里这部分计入"第 3 日及以后"（`:70-75`）。我复现了（`d0=10,d1=12,d2=15,d3=null,d5=20,d7=22`：分布 D3=0、D4–D5=0、D6–D7=2；堆叠第 3 日及以后=7）。理由：任务书和规格写"未到期的格子不计入"，两个边界列缺一个时这一档无法算差；堆叠的最后一段本来就是"D2 之后到最后到期列"，不需要中间边界。只在落地有缺口时出现。
2. 部分格子缺失的算术：`d1=null, d2=15, d3=18`：分布 D1/D2=0，D3=3；堆叠只出现同日和第 3 日及以后。符合"两列都有值才计入，缺一列不当 0"，变异 M13（缺失按 0 算）被测试抓住。
3. `null` 与 0：`known()`（`conversion.ts:20-21`）只排除 `null`/`undefined`/非有限数，真 0 照常计入；日报分母 0 为"—"，额度分母 ≤ 0 为"—"，`configuredTotalSeconds=0` 显示"0 分钟"而不是"未配置"（契约没写清，已在问题文件第一条提出，暂定做法合理）。
4. 三个汇总依次而不是同时调用：规格"同时调"指一个条覆盖三个汇总；顺序调用并在第一次失败时停止，与共用 `LandBar` 的约定一致。
5. 平台筛选没有 `unknown`：规格 5.4 只写了 `ALL/ANDROID/IOS`，契约是否支持已写成问题文件第三条。
6. 统计日 UTC：默认范围、落地默认日期都走 `lastNDaysUtc`/`yesterdayUtc`，测试在 Pacific/Auckland 下守着；`HeaderWithTip` 从 `GuestDailyTab.tsx` 导出给额度页签用，不是缺陷。
