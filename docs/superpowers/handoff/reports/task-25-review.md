## 六、立即修（1）

### 立即修 1：批量导入的 CSV 文件一律按 UTF-8 读，不是 UTF-8 的文件里的备注被静默换成替换符号后照样导入

位置：`src/pages/campaign/BatchModal.tsx:80`（`setCsvText(await chosen.text())`）；`:78-83` 的失败分支只处理"读不出来"。

触发步骤：
1. 运营人员用 Excel 在 Windows 上把成本表另存为"CSV（逗号分隔）"（默认编码是系统的 ANSI 代码页：西班牙语、印尼语是 Windows-1252，简体中文是 GBK），备注里有"campaña de verano"或中文。
2. 打开"批量录入"，CSV 页签，选这个文件。
3. 浏览器的 `File.text()` 总是按 UTF-8 解码，不认识的字节变成 U+FFFD；`parseCostBatch` 不检查备注里有没有替换符号。

错误结果：页面显示"N 行……可以导入"，导入按钮可用，按下后请求体里的备注是 `campa�a de verano; ���`，后端存下乱码。没有任何提示。编码和金额、日期、编码的字符都是 ASCII，不受影响，所以问题只落在备注，但这是静默写入错误的内容，而且这个功能的对象（泰语、阿拉伯语、中文、西班牙语备注）正是最容易遇到非 UTF-8 文件的人。页面和模板只写了"一个 .csv 文件，逗号分隔"，没有说要 UTF-8。

复现：我在拷贝里写了一个一次性页面测试（`t25r/t25r-probe.test.tsx`，已不在拷贝里），用 `0xF1`（Windows-1252 的 ñ）和 GBK 的 `C4 E3 BA C3` 构造文件，经页面选择：导入按钮可用，实际发出的备注是 `"campa�a de verano; ���"`（结果在 `t25r/ansi.json`：`enabled:true`、`hasFFFD:true`）。

如果带着它上线的后果：备注乱码入库；管理员要逐笔改，或者根本没发现。不影响金额。

修法：读文件时用 `new TextDecoder('utf-8', { fatal: true })` 解码 `await chosen.arrayBuffer()`，失败就走已有的"读取文件失败"分支，改成一条明确的文字"文件不是 UTF-8 编码，请另存为 CSV UTF-8"；JSON 文本框里粘贴不会有这个问题。带测试：用上面的字节构造文件，期望不出现"可以导入"、没有写请求。
