## 不是缺陷

1. 播放器出错后自动再取一次内容（多写一条审计日志）：可以接受，不违反契约。理由：契约 §17.4 写的是 `GET …/content` "写审计日志"，没有"一次查看一条"这个约定；每次 GET 签发一个新的签名地址，写一条记录正是准确的记账；规格 5.8 要求"过期后重新取，不缓存"，自动重取是它的实现；次数有上限（`ContentPanel.tsx:97、129-130` 的 `retried`，每次进入页面最多自动一次，之后只能由人点"重新取内容"）。页面上写的"每次查看都会写进审计日志"也仍然准确。小的代价：任何媒体错误（文件损坏、浏览器不支持的格式）都会触发这一次，而不只是过期。
2. 开发模式下严格模式导致取两次（作者记录项 4 的后半）：这个项目没有开严格模式。`src/.umi` 和 `node_modules/@umijs/renderer-react` 里搜不到 `StrictMode`；`ContentPanel` 的 effect 本来也有清理。
3. 详情页给只有 `MODERATION:VIEW` 的管理员显示 `contentRef`（`detail.tsx` 的"内容引用"）：这是契约 §18 里 `ModerationRecord` 的列，`GET /moderation/records/{id}` 要的就是 VIEW；它是存储引用，不是可访问的地址（要经过 `…/content` 签发，且要 REVIEW）。
4. 假后端不把规则页的保存同步到 `GET /config`（作者记录项 2）：只是假后端；真后端是否同步已在问题文件第六条里问了。
5. 来源为投诉的照片、声音按"已有资产"一行显示后果（作者记录项 5）：契约 §11.6 说投诉记录是删除形象之后写的、供统计，不会是待复核，所以不会进判定弹窗。`effects.ts` 的判断（`source !== 'AUTO'`）对待复核的记录只会遇到举报。
6. 路由里 `/moderation/:id` 排在 `/moderation/rules`、`/moderation/stats` 前面：`config/routes/moderation.ts`。路径匹配按具体程度排序，静态路径优先；`config/routes/moderation.test.ts` 用项目自己的页面索引验证了这三个路径各自对应自己的页面，作者的真浏览器检查也打开了规则页和统计页。
7. `REGEX` 的前端提示用 `new RegExp(pattern, 'iu')`（`ruleRows.ts` 的 `regexCompiles`）：带 `u` 标志对 Java 合法的写法（例如 `\_`）也可能给出提示。任务书只要求"不阻止保存的提示"，提示文字已写明"后端用 Java 语法，以后端为准"，变异 `REGEX` 提示变成阻止保存时测试变红，所以是正确的取舍。
