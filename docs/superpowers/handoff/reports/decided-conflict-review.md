## 三、记录（6）

**1. 客户端配置只要两边都有 `updatedAt` 就只比时间，不比内容；时间不变而内容变了的情形发现不了。**
- 位置：`src/pages/clientConfig/version.ts:28-29`（`if (before !== null && now !== null) return before === now;`），被 `ClientConfigEditor.tsx:147`、`:210` 调用。
- 触发步骤：契约把 `GET /client-config` 的键级 `updatedAt` 定义成"各语言行里最近更新的那一行"（`docs/shared-snapshots/backend-task-java-backend.md` 17.4 附表里 `GET /client-config` 一条，第 2364 行），没有写 `PUT` 整体替换时是否给没变的语言行也更新时间。设后端只改动有变化的行：A 打开有 `th`、`ar` 两个语言的键（最近时间 T1）；B 把 `ar` 去掉并保存，剩下的 `th` 行的时间还是 T1；A 改了 `th` 并保存。两次读到的 `updatedAt` 都是 T1，`sameVersion` 返回一致，`PUT` 发出，B 的删除被覆盖回来。
- 错误结果：静默覆盖，正是决定要防的。当前假后端每次保存给所有行同一个新时间，所以测试里碰不到。
- 为什么是记录不是立即修：要靠后端的一种未写明的实现才会出现。建议一并修：时间相同时也比一次内容（只会更严，不会漏报）；并在问题文件里问后端"整体替换时没变的语言行的 `updatedAt` 是否更新"。
- 毫秒/秒精度同理：如果后端的时间只到秒，同一秒内的两次保存也分不出，同一个修法覆盖。

**2. 自己的保存在回复丢失后再按一次，会被报成"已被他人修改"。**
- 位置：`ClientConfigEditor.tsx:155-173`、`rules.tsx:125-142`，与 `:147` / `:115` 的检查。

- 错误结果：数据没有丢（自己的修改已经在库里，点"重新载入"就看到），但提示把自己的写入说成别人的，用户会困惑；"重新载入"丢弃的草稿其实已经保存。是按代码推演的，我没有单独造这个场景复现。

## 四、不是缺陷

1. **比较基准是列表行，不是"点开抽屉那一刻"重新读的。** `list.tsx:137`、`ClientConfigEditor.tsx:77`。页面开了几小时后点开一个键，抽屉显示的是页面载入时的值；别人在这期间改过，用户改完点保存会得到"已被他人修改"。这是正确的方向：用户基于过期内容编辑，系统拦住了，不会覆盖；唯一的不准是提示写"在你打开之后被别人改过"。如果负责人要的是"点开抽屉时就重读并显示最新"，那是新增行为（打开时多一次读取和加载状态），属于变更，要另行确认，不是这次的遗漏。
2. **检查读取要拉回全部 19 个键。** 没有单键读取接口，`readClientConfigKey` 取列表再挑；键数固定且很少，报告已写明。
3. **读和写之间仍有时间窗。** 只有后端在 `PUT` 里比较才能关上；前端能做的一层已做，请求写在问题文件里（契约缺口不是阻塞）。
4. **前端不把 `expectedUpdatedAt` 放进请求体。** 后端未承诺接受，发了可能整体被拒；假后端先支持。同意。
5. **规则词表的假后端没有 `updatedAt`/`expectedUpdatedAt`。** 与现有后端输入一致，"别人在中间改了"靠 `simulateOtherRuleListEdit` 模拟。
6. **检查读取失败时不保存并显示错误码文字。** 这是应有的行为，两个页面都有测试（403 用例）。
7. **警告条在抽屉正文顶部，重置按钮在底部。** 抽屉内容很长时点重置后警告条可能在视口外；已有的失败条是同样的位置，是这个抽屉原有的布局，不是这次引入的。
