# 给后端的问题：四类“只能授出自己持有的权限”的 403 要有结构化原因；`GET /me` 的 `permissions` 是否等于“持有的码”

> **写给：** AvatarBackend 会话（后端）和改契约的会话。
> **来源：** 管理端前端处理后端第一批交付的清单行 a1（管理员只能授出自己持有的权限）。清单里这四类拒绝都答 403 `ADMIN_FORBIDDEN`、`data` 为 `null`，只靠 `message` 的英文句子区分。

## 一、四类 403 需要 `data.reason`

**现状：** 违反规则时返回 403 `ADMIN_FORBIDDEN`，`data` 为 `null`。区分四种情形只有英文 `message`：
1. 只能授出自己持有的权限（`POST /roles`、`PUT /roles/{id}` 的请求码、`POST/PUT /admins` 的 `roleIds`）；
2. 不能改自己持有的角色（`PUT /roles/{id}`）；
3. 只能改权限都在自己持有范围内的角色（`PUT/DELETE /roles/{id}` 的原有码）；
4. 只能对权限都在自己持有范围内的管理员操作（`PUT /admins/{id}`、`POST …/status`、`…/reset-password`、`…/reset-totp`、`DELETE /admins/{id}`）。

**我们为什么需要：** 负责人已定：错误码已知时界面只显示按码翻译的文字，不显示后端 `message`（`message` 是英文，界面只有简体中文和英文，且 `message` 可能随版本改动）。`ADMIN_FORBIDDEN` 同时用于“没有这个接口的权限”“动自己的账号”“必须先改密码”和上面四类，只看码，界面只能写一句覆盖四类规则的通用话，操作者看不出具体是哪一条挡住了自己。

**请求：** 这四类 403 的 `data` 改为 `{"reason": "<代码>"}`，例如 `GRANT_NOT_HELD`、`OWN_ROLE`、`ROLE_NOT_HELD`、`ADMIN_NOT_HELD`（名称由后端定）。前端按 `reason.<代码>` 加译文，把对应那一条写给操作者；`data` 里没有 `reason` 时继续用现在的通用句子。其他原因的 403 保持 `data: null`。

**暂定做法（前端和假后端）：** 通用一句（`system.scopeHint`，管理员页是 `system.admins.forbiddenHint`）：“管理员只能授出自己持有的权限；不能修改自己持有的角色；只能修改权限都在自己持有范围内的角色和管理员。什么都没有改变。”403 不跳转、不退出登录；会话层按既有做法提示并重新读取 `GET /me` 一次。

## 二、`GET /me` 的 `permissions` 是否正好等于规则里“持有的权限码”

清单第 4 节第 5 条没有核实。前端据此做了一个只起辅助作用的处理：非超级管理员在角色权限树里，`permissions` 里没有的节点**预先禁用**（显示，但不能勾选或取消；勾选父节点时只带上持有的后代）。后端仍是最终裁决，收到 403 就按上面的句子显示。

**问：**
1. 对非超级管理员，`GET /me` 的 `permissions` 是否就是“各角色权限码的并集”（后端保存时读数据库的那个集合）？有没有“`permissions` 里有、规则里算没有”或相反的码（例如页面码、自定义节点、已删除的节点）？
2. 如果两者不同，请给出规则所用集合的读取方式（例如在 `GET /me` 里加 `grantablePermissions`），前端就按它禁用。

**如果不同会怎样：** `permissions` 比“持有”多时，前端不禁用的节点后端会拒绝（403，页面显示上面的句子）；`permissions` 比“持有”少时，前端会禁用后端其实允许授出的节点，操作者在这个页面授不出，需要换有权限的人来做。

## 三、“不能改自己持有的角色”：页面不知道哪些角色是操作者自己的

规则 ② 要求操作者不能改自己被分配的角色，但 `GET /me` 没有角色 ID，`GET /roles` 的行也没有“是不是我的”这一项，所以角色页不能在行上预先禁用“编辑”，只能在后端答 403 后显示上面的句子。

**请求（任选其一）：** `GET /me` 增加 `roleIds`（字符串数组），或 `GET /roles` 的每行增加 `heldByMe`（布尔）。有了它，页面可以对这一行的“编辑”直接禁用并写明原因（和管理员页对自己那一行的做法一致）。
