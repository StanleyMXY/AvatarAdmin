# 给后端的问题：新增的告警类型里没写清的几处

> **写给：** AvatarBackend 会话（后端）和改契约的会话。
> **来源：** 管理端前端，根据 `docs/backend-inputs/2026-10-29-avatar-backend-d1-admin-frontend-changes.md` 的 b1、b2、第 4 节第 6 条、第 4 节第 7 条和 GROUP A。下面每一处前端和假后端都已经按"暂定做法"做完，不是阻塞。

## 一、`SUBSCRIPTION_EVENT_FAILED` 告警的内容

后端清单只在第 4 节第 6 条里点了这个类型的名字，没有它的 `refType`、`refId`、`accountId`、`detail` 取值，也没有自动解决的条件。

**问：**
1. `refType` 和 `refId` 各是什么（订阅事件的 id？商店订单号？）？
2. `accountId` 有没有值（决定"关联账号"一栏能不能点进用户详情）？
3. `detail` 是固定取值，还是异常类名、还是错误文字？有哪些固定取值？
4. 什么时候自动解决，管理员能不能手动关闭（`POST /alerts/{id}/resolve`）？关闭有没有副作用？
5. 运营看到这条告警后应该做什么（例如去订阅事件页重放，还是等后端自己重试）？

**我们为什么需要：** 告警页要让运营明白这条告警指的是哪个对象、要不要处理。

**暂定做法：** 筛选里有这个类型（中文"订阅事件处理失败"，英文 "Subscription event processing failed"，名字取自类型名）；`refType`、`refId`、`detail` 原样显示（任何类型的值都当文字显示，对象显示成 JSON），不加任何说明文字；`accountId` 有值就是可点的链接，没有就显示"—"。假后端里这个类型的样例告警按这个做，不自动解决。

## 二、`POSTBACK_CREDENTIAL_FAILED` 的"重新填写"是什么算

清单 b2 写：管理员"重新填写令牌或像素 id（`PUT /attribution/campaigns/{id}`）时"告警自动 `RESOLVED`。`PUT` 的请求体每次都带全部字段。

**问：** 请求里像素 id 和库里存的一样（只改了名字）算"重新填写"吗？请求里没有令牌字段算不算？

**我们为什么需要：** 前端的编辑对话框每次保存都会带上像素 id；如果只要带了就算，运营改个备注也会把还没修好的告警关掉，页面上就没有任何提示了。

**暂定做法：** 假后端只在（一）请求里有新令牌，或（二）像素 id 和保存的不同，这两种情况下关闭告警；只改名字等其他字段时告警保持打开。真实后端若不是这样，请告诉我们，页面不用改，只改假后端。

## 三、`POSTBACK_CREDENTIAL_FAILED` 的 `detail` 取值是平台错误码时

清单 b2 说 `detail` 可能是广告平台返回的错误码（可能为空）。前端对 `token_unreadable`、`pixel_id_malformed` 两个固定值按码翻译成文字（旁边仍写出原值），对其它值（平台错误码）原样显示，为空显示"—"。

**问：** 平台错误码的写法有没有固定形式（纯数字？带子码？），有没有长度上限？如果有，请告诉我们，列里按这个宽度排版。

**暂定做法：** 当作任意文字，过长的用省略加弹层显示完整内容。
