# 给后端的变更请求：已删除或被停用管理员的令牌在管理端接口上的应答

> **写给：** AvatarBackend 会话（后端）和改契约的会话（契约正本在 AvatarApp 的 main，本仓库只读）。
> **来源：** 管理端前端对提交 `be08e85`（账号读不到时显示“服务暂时不可用”并提供“退出登录”）的独立评审，见 `docs/superpowers/handoff/reports/session-unavailable-review.md` 的记录项第 2 条。

## 缺口

契约 17.2 写明：管理员被停用、重置密码、重置二次验证之后，其令牌立即失效，下一次请求答 401 `ADMIN_INVALID_TOKEN`。但 `DELETE /admins/{id}` 删除管理员之后，该管理员已经持有的令牌下一次请求会得到什么，契约没有写。如果后端答 403、404 或 500，前端无法区分“账号没了”和“后端暂时出错”：人会停在“服务暂时不可用”页，“重试”永远不会好，只能点“退出登录”离开。

前端不会把 403 或 404 猜成“账号没了”而自动退出：403 在本项目里的意思是“已认证但没有这个权限”（规格“关键设计点”表的“错误处理”行：403 `ADMIN_FORBIDDEN` 提示无权限、不跳转），据此强制下线会把一次权限抖动变成下线。只有 401 `ADMIN_INVALID_TOKEN` 被当作会话结束。所以正确的修法在后端。

## 变更请求

- **名称：** 已删除或被停用管理员的令牌在管理端接口上的应答。
- **行为：** `DELETE /admins/{id}` 成功之后，该管理员已签发的令牌与停用时一样立即失效；令牌验证按 `tokenVersion`、管理员是否存在和 `status` 判断，找不到管理员也算令牌无效。
- **检查顺序：** 先验令牌签名和有效期；再按 id 取管理员；取不到，或 `status` 不是启用，或 `tokenVersion` 不相等，答 401 `ADMIN_INVALID_TOKEN`；然后才是权限码检查。
- **错误：** 401 `ADMIN_INVALID_TOKEN`，不是 403、404、500。
- **测试：** 删除一个管理员，用它删除前签发的令牌调 `GET /api/admin/me` 和一个带权限码的接口，两者都答 401 `ADMIN_INVALID_TOKEN`；停用、重置密码、重置二次验证同样。

## 前端在收到这个修复之前怎么做

按现有做法继续：令牌还在而 `/me` 读不到时，显示“服务暂时不可用，请稍后重试”，页面上有“重试”和“退出登录”，人不会被困住。对 403、404 这句话不够准确，但不阻塞，也没有对这两种应答做任何猜测。
